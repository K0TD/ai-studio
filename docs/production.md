# Production: установка, обслуживание и восстановление

## Предварительные условия

VPS с Docker Engine и Docker Compose v2, доменное имя с A/AAAA на VPS, открытые входящие 80/443, доступ к RouterAI и внешнему S3/SFTP/restic-хранилищу. Docker socket не передается приложению. Для cron нужны host `flock` и права на Docker; доступ к Docker эквивалентен root.

Стек: Caddy TLS → Next.js web и отдельный worker. При пустом `DATABASE_URL` используется SQLite в `./storage/database/studio.sqlite`; web и worker монтируют один каталог `./storage`. PostgreSQL включается явно через профиль `postgres` и соответствующий `DATABASE_URL`. Медиа хранятся в volume `media`, принадлежащем UID/GID 1001. Порты PostgreSQL и web доступны только на localhost; Caddy публикует 80/443. Web и worker запускаются без root, с read-only корнем и ограниченными временными каталогами.

Базовые образы закреплены версиями. Перед каждым production-релизом проверьте наличие и уязвимости образов; обновляйте версии отдельным проверенным изменением. Наличие Dockerfile само по себе не означает, что сервис развернут и прошел приемку.

## Первый запуск

1. Скопируйте `.env.example` в `.env`, установите права `0600` и заполните настройки. `APP_DOMAIN` — только hostname; `BETTER_AUTH_URL` — соответствующий `https://...`. Задайте уникальные `POSTGRES_PASSWORD`, `BETTER_AUTH_SECRET` (минимум 32 символа), `ADMIN_PASSWORD` (минимум 12 символов), `ADMIN_LOGIN` и `ROUTERAI_API_KEY`. Для генерации секретов используйте менеджер паролей либо `openssl rand -hex 32`.
2. Для SQLite оставьте `DATABASE_URL` пустым. Для PostgreSQL задайте URL на `postgres:5432` и согласованные `POSTGRES_*`, включите профиль `postgres`; URL-кодируйте специальные символы пароля. Не меняйте тип БД между обновлениями без отдельного переноса данных. Для версии образа задайте уникальный `APP_IMAGE_TAG`, например идентификатор релиза.
3. Подготовьте резервирование по следующему разделу. Храните пароль restic вне VPS также: его потеря делает зашифрованные копии бесполезными.
4. Выполните из корня проекта:

```sh
docker compose --env-file .env config -q
docker compose build web backup
docker compose up -d media-init
docker compose run --rm --no-deps web bun run preflight
docker compose --profile ops run --rm init
docker compose --profile caddy up -d web worker caddy
docker compose ps
```

Команды выше используют SQLite. Для PostgreSQL сначала запустите `docker compose --profile postgres up -d postgres media-init`. `init` выполняется до приема запросов; web также проверяет схему и синхронизирует защищенного администратора при старте. При существующей БД сначала создайте резервную копию и проверьте миграции на ее восстановленной копии. Не применяйте `drizzle-kit push` в production.

`docker compose up -d --build` сохраняет bind mount `./storage` и именованный media volume. Не удаляйте `storage`, не запускайте `down -v` и не меняйте путь Compose-проекта при обновлении. SQLite-файлы и журналы исключены из build context и не входят в образ. Наличие `database.auto_migrate_success` означает проверку схемы, а не создание новой БД. Для диагностики сравнивайте ID пользователей/заданий и количество записей до и после обновления.

Проверка сохранности на отдельном временном Compose-проекте: `APP_IMAGE_TAG=<собранный-тег> sh ops/verify-sqlite-persistence.sh`. Флаг `--build` также пересобирает образ в обоих циклах проверки. Нужен Compose ≥ 2.24.4. Скрипт использует тестовые настройки, изолированные bind mounts в `/tmp`, динамический localhost-порт и worker без сети; проверяет БД, финансовый журнал, медиа и старые логи после двух пересозданий, затем удаляет только свое окружение.

Откройте `https://<домен>/admin/login`. Создайте пользователя, передайте одноразовую ссылку защищенным каналом, назначьте модели/разделы и лимиты, начислите баланс с причиной. Новый пользователь не получает доступ и деньги автоматически.

## Проверка и наблюдение

```sh
curl --fail https://<домен>/api/health/live
curl --fail https://<домен>/api/health/ready
docker compose ps
docker compose logs --tail=100 web worker
```

Настройте внешнее наблюдение HTTPS readiness и предупреждения об unhealthy контейнерах, отсутствии heartbeat worker, зависших `reconciling` заданиях, превышении стоимости и сбоях резервирования. Docker отмечает unhealthy, но сам по себе не перезапускает зависший процесс: внешний монитор должен уведомлять оператора. Readiness не проверяет платным запросом доступность генерации RouterAI.

Логи приложения сохраняются в `storage/logs/web.jsonl`, `worker.jsonl` и `startup.jsonl` и остаются после пересоздания контейнера. Каждая строка содержит время UTC, уровень, сервис и детали события. Файл ротируется после 10 MiB, сохраняются пять архивов `.1`–`.5`; Docker stdout также ротируется независимо. Ключи, пароли, cookies, токены, параметры ссылок и бинарные данные очищаются перед записью. Событие `logging.write_failed` в stdout означает проблему файловой записи; проверьте диск и права UID 1001. Не включайте shell `set -x`, печать cookie/приглашений либо `docker compose config` без `-q`. Не публикуйте снимки окружения.

Для генерации событие `generation.accepted` связывает `requestId` HTTP-запроса с `jobId`. В `worker.jsonl` по `jobId` видны получение задания, модель и раздел, запрос/ответ провайдера, длительность, наличие и размер сохранённого файла, повторы и итоговое списание. Промпты, содержимое файлов и подписанные URL в эти события не записываются. Ищите цепочку, например: `rg '"jobId":"<id>"' storage/logs/worker.jsonl`.

Перед генерацией сумма отображается как резерв, а не как списание. Резерв закрывается после успешного сохранения результата и сверки стоимости. Если синхронный image endpoint подтвердил HTTP 200, но не вернул пригодную картинку, задание завершается без списания и резерв освобождается. Неизвестный исход POST не отправляется повторно: если за 15 минут нет ни результата, ни ID задания провайдера, задание помечается неуспешным и резерв возвращается; если ID есть, задание остаётся в `reconciling` для сверки администратором.

## Зашифрованные внешние резервные копии

Образ `ops/Dockerfile.backup` содержит PostgreSQL client, SQLite CLI и restic; установка пакетов во время резервирования не нужна. Задайте `RESTIC_REPOSITORY` с внешним адресом: `s3:`, `sftp:`, `rest:https://`, `b2:`, `gs:` или `azure:`. Для S3 используются `BACKUP_AWS_*`. Для SFTP дополнительно предоставьте отдельные SSH credentials/known_hosts в backup-контейнер; штатный Compose настроен для S3.

Создайте `secrets/restic-password` с криптографически случайным паролем. Файл должен принадлежать UID/GID `1001:1001`, иметь режим `0400`, родительский каталог `0700`. Файл исключен из build context; приложение его не монтирует. Сохраните независимую копию пароля и реквизитов хранилища вне VPS.

```sh
docker compose --profile ops run --rm backup init
./ops/backup-host.sh
docker compose --profile ops run --rm backup check
```

`backup-host.sh` кратковременно останавливает web и worker для согласованной копии БД и media. Для SQLite создается snapshot через `.backup` с учетом WAL и проверками `integrity_check`/`foreign_key_check`; для PostgreSQL выполняется `pg_dump -Fc` по `DATABASE_URL`. Снимок содержит БД, media и manifest с типом БД. Скрипт отправляет его в зашифрованный restic и возобновляет процессы даже при ошибке. Во время паузы Caddy возвращает недоступность; планируйте окно обслуживания. Перед запуском сервисы web/worker должны работать; скрипт предполагает, что оба необходимо возобновить. Журналы приложения не входят в snapshot БД.

Промежуточные архивы и кеш restic используют приватный дисковый volume `backup_work`, а не оперативную память контейнера. Свободного места должно хватать на дамп БД, полный архив media и кеш; следите за заполнением диска. После успешного завершения и обычной ошибки временные архивы удаляются; после аварийного отключения проверьте и очистите оставшиеся staging-каталоги перед следующей копией.

Ежедневно, например из root crontab:

```cron
15 3 * * * /srv/studio/ops/backup-host.sh >> /var/log/studio-backup.log 2>&1
```

Настройте ротацию этого журнала и уведомление о ненулевом коде cron, контролируйте время последнего снимка во внешнем хранилище. Хранятся все снимки за последние 30 дней; `restic forget --prune` удаляет более старые. Резервирование проверяет структуру репозитория; еженедельный `backup check` полностью читает данные. Защитите внешнее хранилище отдельной учетной записью и механизмом удержания/версий по возможностям провайдера.

## Восстановление и учебная проверка

Проводите проверку восстановления на отдельном VPS/Compose-проекте минимум перед первым запуском, после изменения схемы и регулярно далее. Не направляйте тестовый `DATABASE_URL` на production. Стандартный запуск backup использует media read-only; для восстановления нужен отдельный override:

```yaml
# /tmp/studio-restore.yml — использовать только для целевого пустого окружения
services:
  backup:
    volumes:
      - media:/data/media
      - ./storage:/app/storage
```

1. Подготовьте отдельный каталог проекта с собственным `storage`, собственное имя Compose-проекта и пустой media volume. Для SQLite файл БД и его `-wal`/`-shm` должны отсутствовать. Для PostgreSQL нужна пустая БД. Тип целевой БД должен совпадать с manifest snapshot. Скопируйте настройки restic и пароль. Не выполняйте миграции до восстановления.
2. Соберите образы и запустите `media-init` (для PostgreSQL также `postgres` с профилем); web/worker оставьте остановленными. При учебной проверке используйте отдельный `--project-name` во всех командах. Одного другого имени проекта недостаточно для изоляции bind mount `./storage`: используйте отдельный каталог или явно замените этот mount в override.
3. Восстановите снимок:

```sh
docker compose -f docker-compose.yml -f /tmp/studio-restore.yml --profile ops run --rm --entrypoint /usr/local/bin/restore.sh -e RESTORE_CONFIRM=EMPTY_DATABASE_AND_MEDIA -e STUDIO_WRITERS_STOPPED=yes backup latest
```

Скрипт отказывается работать с существующим SQLite-файлом/sidecar, непустой PostgreSQL БД или media. SQLite snapshot проверяется до копирования; `pg_restore` выполняется одной транзакцией. Старые snapshot формата 1 распознаются как PostgreSQL. Медиа восстанавливаются от UID 1001. При ошибке оставьте процессы остановленными; повторяйте только на новом пустом окружении. Между восстановлением БД и media нет общей транзакции.

4. Сначала проверьте целостность: суммы `balanceRub >= reservedRub >= 0`, историю транзакций, количество пользователей/заданий и наличие нескольких медиафайлов. Затем примените только требуемые для выбранной версии приложения миграции и синхронизируйте администратора.
5. На учебном стенде не запускайте worker с настоящим ключом RouterAI до разбора незавершенных заданий: иначе восстановленные очереди могут начать реальную генерацию. Проверьте их вручную, сверяйте отправленные задачи с провайдером. Готовые результаты, баланс, права и защищенные загрузки должны открываться через web.
6. Запишите дату, ID снимка, время восстановления, результаты проверок и замечания. Документ не утверждает, что учебное восстановление уже выполнено.

## Обновления и смена администратора

Сначала проверьте CI и восстановление текущей копии. Сохраните номер образа и версию схемы. Соберите новый образ с новым `APP_IMAGE_TAG`, остановите прием заданий, выполните согласованную резервную копию и остановите web/worker перед миграциями. Затем выполните `init` и запустите новую версию. Ручной откат приложения допускается лишь при совместимой схеме; иначе восстанавливайте БД и media из соответствующей копии в пустые volumes. Не выполняйте `docker compose down -v` на production.

Для смены основного логина/пароля обновите `.env` и выполните `docker compose up -d --force-recreate web worker`. Перед приемом запросов web синхронизирует тот же защищенный аккаунт и отзывает прежние сессии, если логин или пароль изменились. Изменение файла без пересоздания контейнеров не меняет их окружение. Для запуска приложения без Docker выполните `bun run sync-admin` перед перезапуском.

## Приемка релиза

Должны пройти typecheck, lint, тесты, build, проверка секретов и зависимостей. На отдельном стенде проверьте: создание аккаунта и приглашение, вход/выход, запреты для анонимного и заблокированного пользователя, выдачу/отзыв доступов, начисление/отзыв доступного баланса, конкурирующие генерации, идемпотентность и восстановление worker после остановки.

Реальные генерации видео, изображения и речи требуют работающего ключа и средств RouterAI; выполняйте их с ограниченным балансом тестового аккаунта. Проверяйте оценку, резерв, фактическую/оценочную цену и одинаковый остаток пользователя и администратора. Только после этих проверок открывайте сервис пользователям.

Проверка в рабочем окружении 2026-10-22: собран backup-образ, проверены restic 0.18.1 и PostgreSQL client 16.13 под UID 1001. Через настоящий `restore.sh` восстановлен зашифрованный локальный тестовый снимок в отдельную БД: 7 учетных записей, 0 нарушений денежных ограничений, байты media-файла совпали. Повторное восстановление в занятую БД и непустой media-каталог отклонено. Локальный restic использовался только как тестовый стенд прямыми CLI-командами; production-скрипт по-прежнему запрещает локальный репозиторий. Отправка копии за пределы VPS требует настроенных реквизитов внешнего хранилища и отдельной проверки.
